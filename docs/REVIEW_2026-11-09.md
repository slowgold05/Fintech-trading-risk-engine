## Must fix before analytics release

### 1. Performance accepts unsupported ranges and labels a two-year calculation as a shorter window

**What this is:** [performance_service.py](../app/services/performance_service.py#L125) validates against the market-chart range set, which now includes `1m`, `3m`, `6m`, and `all`.

**Problem:** Only `1y` selects a one-year start; every other accepted token selects a two-year start. An isolated authenticated request for `/portfolio/performance?range=1m`, with the clock fixed at 2026-11-09, returned HTTP 200, `range: 1m`, and `requested_start: 2024-11-09`. The risk-metrics route reuses this reader. Existing invalid-range tests do not exercise these chart tokens.

**Fix:** Give performance its own `1y`/`2y` allowlist, and reject the other chart tokens in both direct-service and HTTP regression cases. Do not change the legitimate chart ranges.

**If skipped:** The response advertises a window different from the one used to calculate the results. This review reproduced the behavior; it does not fix the service.

### 2. A valid zero-value account can crash performance and risk calculations

**What this is:** Performance divides by the previous account value and running peak. Modified Dietz divides by weighted invested capital. Fixed stress percentages divide by account value.

**Problem:** [performance_service.py](../app/services/performance_service.py#L201) and its Dietz helper, plus [portfolio_risk.py](../app/services/portfolio_risk.py#L325), do not guard all zero denominators. An isolated account with its entire cash balance withdrawn through the real cash service raised a Decimal exception on the performance read. Separate direct probes reproduced the Dietz zero-capital denominator and a complete empty allocation's stress-percentage failure.

**Fix:** Define unavailable return/drawdown percentages for zero-capital periods, preserve known cash and dollar P&L, and carry that definition through the risk reader and frontend. Add withdrawal-to-zero, subsequent empty days, re-funding, and zero-weighted-capital regressions. Avoid a blanket replacement with fabricated zero returns.

**If skipped:** Legitimate empty accounts can get HTTP 500 from the analytics routes. The correction needs a small explicit calculation contract and caller tests; this documentation task leaves it open.

## Should fix before enabling broader use

### 3. The risk response combines separate database snapshots

**What this is:** [build_risk_metrics_response](../app/services/portfolio_risk.py#L444) composes performance, holding/correlation, and allocation reads.

**Problem:** These readers are not joined into one owned snapshot. The shared [consistent_read](../app/core/read_snapshot.py#L52) helper rolls back at entry and exit, so successive public-reader calls can see different committed state. A fill between the performance and allocation reads can combine pre-fill history with post-fill weights while the response publishes the performance read's timestamp. This is established by tracing the transaction boundaries; a new concurrency reproduction was not run for this finding.

**Fix:** Compose the needed internal reads within one transaction and clock. Simply putting an outer `consistent_read` around the current public readers is insufficient because their nested calls roll it back. Prove consistency with a second-session commit during the read.

**If skipped:** The published fields need not describe one account snapshot, even when each field is independently valid.

### 4. Pending-job limits are not atomic

**What this is:** Research intake caps pending jobs at 10; forecast intake caps them at 5.

**Problem:** [research.py](../app/routers/research.py#L78) and [forecasts.py](../app/routers/forecasts.py#L87) count queued/running rows and then insert without serializing admission for that owner. With 9 research jobs, two concurrent requests can both count 9 and commit an eleventh job; the equivalent forecast case starts at 4 and ends at 6. Authentication does not acquire an owner lock. This finding comes from the reachable count/insert interleaving; this review did not run a new PostgreSQL race test for it.

**Fix:** Serialize admission on a stable owner row, using the repository's existing row-locking patterns, and prove the boundary with two independent PostgreSQL sessions. Preserve role-column restrictions and the SQLite test path.

**If skipped:** A per-owner pending-job cap can be exceeded under concurrent submissions. Per-cycle scheduler limits do not make the intake cap atomic.
